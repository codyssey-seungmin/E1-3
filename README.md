# Mini NPU Simulator — E1-3

입력 패턴과 필터의 같은 위치에 있는 값을 곱하고 누적하는 MAC(Multiply-Accumulate) 연산으로 패턴을 판정하는 Python 콘솔 프로그램입니다.

## 실행 방법

Python 3.8 이상에서 실행하며, 외부 라이브러리를 설치할 필요가 없습니다.
`main.py`와 과제에서 제공한 원본 `data.json`을 같은 폴더에 둡니다.

```powershell
python main.py
```

- `1`: 3×3 필터 A, 필터 B, 패턴을 각각 3줄씩 입력합니다.
- `2`: `data.json`의 필터와 패턴을 분석합니다.
- `3`: 크기 N을 입력하면 N×N Cross와 X를 자동 생성하고 점수·판정·10회 평균 연산 시간을 출력합니다.

모드 1에서 숫자를 입력하는 대신 각 표의 첫 줄에 `Cross` 또는 `X`를 입력하면 해당 3×3 표를 자동 생성합니다.

JSON 경로는 `Path(__file__).parent`를 기준으로 정하므로 실행한 터미널의 위치와 관계없이 `main.py` 옆의 파일을 읽습니다.

## 구현 요약

| 기능 | 담당 함수 | 동작 |
| --- | --- | --- |
| MAC 계산 | `calculate_mac` | 이중 반복문으로 위치별 곱셈과 누적 합산 |
| 점수 비교 | `compare_scores` | 차이의 절댓값이 `EPSILON = 1e-9` 미만이면 `UNDECIDED`, 그 외에는 A 또는 B |
| 콘솔 입력 | `read_matrix` | 각 행에 숫자 3개 입력, 열 개수와 숫자 변환 오류 시 같은 행 재입력 |
| 파일 읽기 | `load_data` | JSON 로드 및 파일 없음·인코딩·JSON 형식 오류 안내 |
| 배열 검사 | `validate_matrix` | 행·열 크기와 숫자 자료형 검사 |
| 라벨 정규화 | `normalize_label` | 공백 제거와 소문자 변환 후 `+`/`cross`를 `Cross`, `x`를 `X`로 통일 |
| 필터 선택 | `get_filters` | 해당 크기 필터 검사 및 정규화된 이름의 중복·누락 검사 |
| 패턴 크기 해석 | `get_pattern_size` | `size_N_idx`에서 양의 정수 N 추출 |
| 개별 판정 | `analyze_pattern` | Cross/X 점수, 표준 라벨 판정, expected 비교 결과 반환 |
| 일괄 분석 | `analyze_all_patterns` | 케이스별 PASS/FAIL 기록, 데이터 오류 발생 시 다음 케이스 계속 처리 |
| 성능 측정 | `measure_mac_time` | `perf_counter`로 MAC 함수 호출을 10회 측정하여 평균 ms 반환 |
| 성능·결과 출력 | `print_performance`, `print_summary` | 크기별 측정 표, 총/통과/실패 수와 실패 목록 출력 |
| 패턴 생성기 (선택 보너스) | `generate_patterns`, `run_generator_mode` | 입력 크기에 맞는 Cross/X 생성 및 판정·성능 측정 |

모드 1에서는 필터 저장 확인 → 패턴 입력 → 점수 및 판정 → 3×3 성능 측정 순서로 실행합니다.
모드 2에서는 필터 로드 확인 → 패턴 분석 → 3×3·5×5·13×13·25×25 성능 측정 → 결과 요약 순서로 실행합니다.

### 실패 원인 및 시간 복잡도 분석

1. 원본 데이터의 필터 키는 `cross`, `x`이고 expected는 `+`, `x`이므로 문자열을 그대로 비교하면 같은 의미도 다르다고 판정할 수 있습니다.
2. 필터 이름과 expected를 모두 `Cross`, `X`로 정규화하여 라벨 표현 차이로 생기는 오판을 방지했습니다.
3. 원본 데이터는 배열 크기와 필수 키 검사를 통과했으며, 이번 3개 FAIL의 원인은 스키마 오류가 아닙니다.
4. `size_5_1`의 두 점수 차이는 약 `1.11e-16`으로 `1e-9`보다 작습니다.
5. `size_13_2`의 두 점수 차이는 약 `2.66e-15`로 `1e-9`보다 작습니다.
6. `size_25_1`의 두 점수 차이는 약 `8.88e-16`으로 `1e-9`보다 작습니다.
7. 이 세 케이스는 허용오차 정책에 따라 모두 `UNDECIDED`로 판정되며, expected는 Cross 또는 X이므로 FAIL로 집계됩니다.
8. 이러한 FAIL은 정한 동점 규칙을 적용한 결과이며, 이 결과만으로 MAC 계산 로직이 틀렸다고 볼 수는 없습니다.
9. 부동소수점은 일부 소수를 정확하게 표현하지 못해 수학적으로 같은 값도 계산 결과에 아주 작은 차이가 생길 수 있습니다.
10. 단순히 `==`와 대소 비교만 사용하면 이런 작은 차이로 승자를 결정할 수 있으므로 먼저 허용오차를 검사합니다.
11. 동점은 두 필터의 겹치는 값의 합만으로 현재 패턴을 구별하기 어렵다는 뜻이며, 데이터·필터 설계도 함께 검토할 수 있습니다.
12. PASS 수를 늘리기 위해 원본 데이터나 expected를 수정하거나, 동점에서 임의로 라벨을 선택하지 않았습니다.
13. 스키마·크기 오류는 예외를 잡아 해당 케이스의 FAIL 사유로 기록하고, 이후 케이스의 분석을 계속합니다.
14. N×N 배열은 N개의 행과 각 행의 N개 원소를 방문하므로 필터 하나의 MAC 누적 횟수는 N²입니다.
15. 각 원소에서 곱셈 한 번과 덧셈 한 번을 수행하므로, 표의 N²는 곱셈과 덧셈을 한 쌍으로 센 MAC 횟수입니다.
16. 필터 두 개를 비교할 때는 2N²번의 MAC을 수행하지만 상수 배수는 차수에 영향을 주지 않아 시간 복잡도는 O(N²)입니다.
17. 크기 검증 역시 원소를 한 번씩 검사하므로 O(N²)이며, 고정된 수의 필터를 검증하고 판정하는 전체 과정도 O(N²)입니다.
18. 입력과 필터를 저장하는 공간은 O(N²)이고, MAC 함수가 계산 중 추가로 사용하는 누적값과 인덱스 공간은 O(1)입니다.

### 성능 측정 결과 및 해석

아래는 Python 3.13.15 환경에서 실제 실행한 10회 평균 측정 예시이며, 실행 환경과 실행 시점에 따라 달라집니다.

| 크기 | 평균 시간(ms) | MAC 횟수(N²) |
| --- | ---: | ---: |
| 3×3 | 0.001770 | 9 |
| 5×5 | 0.002230 | 25 |
| 13×13 | 0.010200 | 169 |
| 25×25 | 0.036270 | 625 |

측정 구간은 `calculate_mac` 함수 호출 전후이며, 입력·출력·파일 읽기·라벨 변환·크기 검증 시간은 제외합니다.
모드 1은 입력 패턴과 필터 A를 사용하고, 모드 2의 3×3은 기본 십자가 배열을 사용합니다.
모드 2의 3×3 기본 십자가 배열은 `generate_patterns(3)`으로 생성하며 생성 시간은 측정에서 제외합니다.
모드 2의 나머지 크기는 각 크기의 Cross 필터를 입력과 필터 양쪽에 사용해 크기에 따른 연산 비용을 비교합니다.
성능 표는 두 필터 판정 전체 시간이 아니라 **필터 하나에 대한 MAC 함수 1회 호출의 평균 시간**입니다.

13×13에서 25×25로 커지면 MAC 횟수는 169에서 625로 약 3.70배 증가하고, 위 측정 시간은 약 3.56배 증가했습니다.
이는 N²에 따라 연산량이 증가한다는 분석과 대체로 맞지만, 10회의 짧은 측정만으로 정확한 시간 비율을 보장할 수는 없습니다.
특히 작은 배열에서는 함수 호출·타이머 비용과 운영체제의 실행 상태가 상대적으로 크게 반영됩니다.
O(N²)의 근거는 반복문의 원소 방문 횟수이며, 시간 표는 그 경향을 확인하는 자료입니다.
이 프로그램은 Python 반복문으로 동작하는 소프트웨어 시뮬레이터이므로 실제 NPU의 병렬 처리 성능을 측정하는 것은 아닙니다.

## 모드별 동점 처리 및 우선순위 (평가 항목 #17)

두 필터의 점수 차이를 먼저 `abs(score_a - score_b) < EPSILON`으로 검사하며, 현재 `EPSILON`은 `1e-9`입니다.
동점 조건을 만족하면 즉시 `UNDECIDED`를 반환하므로 A나 Cross를 우선 선택하지 않습니다.
동점이 아닐 때만 대소 비교로 A/B를 결정합니다. 차이가 정확히 EPSILON이면 `<` 조건에 해당하지 않으므로 큰 점수 쪽을 선택합니다.

| 구분 | 모드 1: 사용자 입력 | 모드 2: JSON 분석 |
| --- | --- | --- |
| 점수 비교 기준 | `compare_scores`와 동일한 EPSILON 사용 | `compare_scores`와 동일한 EPSILON 사용 |
| 일반 판정 | A 또는 B | A를 Cross, B를 X로 변환해 출력 |
| 동점 판정 | `판정: UNDECIDED` 출력, 판정 불가를 의미 | `판정: UNDECIDED` 출력 |
| expected 비교 | 정답 라벨이 없으므로 PASS/FAIL 집계 없음 | 정규화된 expected와 비교; Cross/X 정답에 UNDECIDED면 FAIL |
| 동점 이후 동작 | 3×3 성능 표 출력 후 종료 | 실패 사유 기록 후 다음 케이스 분석; 성능 표와 전체 요약 출력 |

예를 들어 두 점수가 `0.9`, `0.8999999999999999`이면 두 모드 모두 동점입니다.
모드 2에서 expected가 `x`라면 `X`로 정규화되며, `UNDECIDED != X`이므로 FAIL 수가 1 증가합니다.
모드 1에서는 같은 동점이라도 비교할 expected가 없어 FAIL 수를 만들지 않습니다.
원본의 동점 3개는 원본 결과 표와 실패 목록에 모두 반영됩니다.
보너스 모드 3도 같은 EPSILON과 Cross/X 이름을 사용하며 expected 기반 집계는 하지 않습니다.

## 새 라벨 추가·확장 절차 (평가 항목 #18)

현재 표준 라벨은 `Cross`, `X` 두 가지이며, 아래는 향후 확장할 때 수행해야 할 절차입니다.

1. **별칭인지 새 종류인지 결정합니다.** 예를 들어 `plus`를 기존 Cross의 별칭으로 추가하는 것과 `Circle`을 세 번째 모양으로 추가하는 것은 변경 범위가 다릅니다. 현재 `plus`와 `Circle`은 지원하지 않습니다.
2. **정규화 규칙을 추가합니다.** 별칭 확장이라면 `normalize_label`의 Cross 조건에 `plus`를 추가합니다. 새 종류라면 표준 이름과 허용 별칭을 정하고 별도 반환 조건을 추가합니다. 공백 제거·소문자 변환 규칙은 함께 적용합니다.
3. **데이터를 업데이트합니다.** 별칭은 해당 필터 키나 expected에 사용할 수 있으나 같은 크기에 `cross`와 `plus`를 동시에 넣으면 정규화 후 중복으로 거부되어야 합니다. 새 종류는 분석할 각 `filters.size_N`에 N×N 필터를 추가하고, `patterns.size_N_idx`에 입력 표와 expected를 추가합니다.
4. **필터 검사와 판정 로직을 업데이트합니다.** 별칭만 추가하면 기존 두 점수 비교를 재사용합니다. 세 번째 종류를 추가할 때는 `get_filters`의 필수 라벨 검사, `analyze_pattern`의 모든 필터 점수 계산, A/B 변환 딕셔너리를 함께 변경해야 합니다. 정규화 함수만 바꾸면 세 번째 모양을 판정할 수 없습니다.
5. **다중 점수의 동점 정책을 정합니다.** 세 종류 이상에서는 가장 높은 점수와 두 번째 점수의 차이가 EPSILON 미만이면 UNDECIDED로 처리하는 정책 등으로 확장하고, 동점에서 임의의 라벨에 우선순위를 주지 않도록 테스트합니다.
6. **출력과 문서를 업데이트합니다.** 개별 결과의 점수 필드, 콘솔 점수 이름, expected 표시, README 라벨 표·결과 표·사용 예시를 수정합니다. 새 종류도 보너스 생성 대상에 넣으려면 생성 규칙과 메뉴 설명을 추가합니다.
7. **테스트 케이스를 추가합니다.** 별칭·대소문자·공백 정규화, 미지원 라벨, 정규화 후 중복 키, 필터 누락, 잘못된 배열 크기, 새 종류 정상 판정, 동점·EPSILON 경계를 검사합니다.
8. **회귀 테스트를 실행합니다.** `python -B -m unittest -v test_main`을 실행하고 기존 모드 1·2·3이 동작하며, 원본 데이터의 총 6개·PASS 3개·FAIL 3개가 유지되는지 확인합니다. 정책이나 데이터를 의도적으로 바꾼 경우에는 변경 근거와 새 예상 결과를 문서에 함께 기록합니다.

## CPU와 NPU의 병목 및 비교 (평가 항목 #20)

현재 프로그램은 CPU에서 Python 이중 반복문을 실행합니다. 한 칸마다 리스트 원소를 읽고 곱한 다음 `total`에 더하며, 이 누적값은 앞선 계산 결과를 사용합니다.
배열 크기가 커지면 N²개의 원소 접근과 Python 반복·인덱싱·숫자 연산 비용이 늘어납니다. CPU도 SIMD와 여러 코어로 병렬 처리할 수 있지만, 현재 코드는 그런 기능을 직접 사용하지 않습니다.

| 관점 | 현재 CPU 기반 시뮬레이터 | 실제 NPU의 일반적 처리 방향 |
| --- | --- | --- |
| 연산 | Python 루프에서 MAC을 차례로 누적 | 다수의 MAC 연산 장치에서 곱셈·부분합을 병렬 처리 |
| 연산 병목 | 반복·인덱싱 비용과 누적 계산; 큰 데이터에서는 캐시·메모리 접근도 영향 | 병렬 장치 수와 사용률, 부분합 결합, 지원 자료형·연산 |
| 데이터 공급 | 리스트와 숫자 객체를 메모리에서 읽음 | 타일 단위로 입력·가중치를 가져와 온칩 메모리에 두고 재사용 |
| 메모리 대역폭 | 데이터 이동이 느리면 연산기가 기다림 | MAC 장치가 많아도 데이터 공급이 부족하면 함께 대기하므로 전송·재사용 최적화가 필요 |

예를 들어 25×25 필터 하나는 625회 MAC, 필터 두 개는 1,250회 MAC이 필요합니다.
설명용으로 MAC 장치 25개가 독립적인 곱셈·부분합을 처리할 수 있다고 가정하면 625개 작업을 25개씩 나눌 수 있습니다. 다만 최종 합산·메모리 전송·장치 사용률이 추가되므로 실제 시간이 정확히 25분의 1이 된다는 뜻은 아닙니다.
필터 1,000개를 비교하면 같은 입력을 여러 필터에 재사용할 수 있어 NPU의 병렬 MAC과 온칩 데이터 재사용이 유리할 수 있습니다.
반대로 3×3 패턴 하나처럼 작은 작업은 NPU에 데이터를 보내고 실행을 준비하는 비용이 연산량보다 커질 수 있어, NPU가 항상 빠르다고 단정할 수 없습니다.
메모리 대역폭은 초당 전달할 수 있는 데이터 양이며, 연산 속도를 높여도 이 공급 속도가 부족하면 병목이 남습니다.
따라서 연산량 O(N²)와 실제 실행 시간, 데이터 전송 비용을 구분해야 합니다. 본 성능 표는 CPU에서 MAC 함수만 측정한 값으로 CPU/NPU 실측 비교가 아닙니다.

근거 자료: [Intel NPU 구조 설명](https://intel.github.io/intel-npu-acceleration-library/npu.html)은 행렬·합성곱 가속, 병렬 실행, SRAM/DRAM 데이터 이동 감소를 설명합니다.
[Intel/Microsoft Brainwave 논문](https://www.intel.la/content/dam/www/public/us/en/documents/white-papers/accelerating-artificial-intelligence-bing-whitepaper.pdf)의 Figure 5와 관련 본문은 병렬 MAC 배열 및 데이터 공급 대역폭의 병목을 설명합니다.

## 선택 보너스: 패턴 생성기

선택한 보너스는 **입력한 N에 맞는 Cross와 X 패턴 자동 생성**입니다.
`generate_patterns(size)`가 두 패턴을 0·1의 2차원 리스트로 만들어 `{"Cross": ..., "X": ...}`로 반환합니다.
Cross는 `row == size // 2` 또는 `col == size // 2`인 칸을 1로, X는 `row == col` 또는 `row + col == size - 1`인 칸을 1로 만듭니다.
N은 1 이상의 정수이며, 짝수 N의 Cross는 0부터 센 `N // 2`번 행·열을 중심선으로 사용합니다. 대칭 모양을 확인하기에는 과제의 3·5·13·25 같은 홀수 크기가 적합합니다.
N=1에서는 Cross와 X가 모두 `[[1]]`이므로 UNDECIDED가 정상이며, N=2에서도 일부 패턴은 MAC 점수가 같을 수 있습니다.
생성기는 N²개 칸을 채우므로 시간과 반환 데이터 공간 모두 O(N²)입니다.

### 실행과 재활용

1. `python main.py` → 모드 `3` → 크기 `5` 입력: 두 표와 각 판정, 5×5 평균 시간·MAC 횟수 25가 출력됩니다. 생성한 Cross/X 자체 점수는 각각 9, 서로의 점수는 1입니다.
2. 모드 `3`에서 `abc`, `0`, 음수나 소수를 입력하면 오류 안내 후 크기를 다시 입력받습니다.
3. 모드 `1` → 필터 A 첫 줄 `Cross` → 필터 B 첫 줄 `X` → 패턴 첫 줄 `X`: A 점수 1.0, B 점수 5.0, 판정 B를 확인할 수 있습니다. 원래의 숫자 3줄 입력도 계속 사용할 수 있습니다.
4. 모드 `2`의 3×3 성능 분석은 같은 생성기를 재사용하며, JSON의 5·13·25 필터와 원본 6개 케이스의 판정 기준은 그대로 사용합니다.

### 자동 검증

표준 라이브러리 `unittest`로 다음 명령을 실행합니다.

```powershell
python -B -m unittest -v test_main
```

`test_main.py`는 생성 표의 기준 모양·크기·점수·잘못된 크기 처리, 수동 입력과 자동 생성, 모드별 동점 표시, 원본 JSON 결과, 10회 시간 측정, 오류 케이스 뒤 분석 지속을 검사합니다.
